# 公链架构 ADR（设计草案，未实现）

> **状态：PROPOSED / 设计草案，尚未实现。**
>
> 本文件不改变当前代码或协议。当前仓库仍是 **单 Coordinator 仲裁 + 静态 peers/邀请码 +
> 本地 SQLite + 本地 CREDIT 账本**；**没有**公链、代币、钱包、链上结算或开放注册实现。

## 1. 背景：当前 Coordinator 仲裁模型的限制

当前系统为了尽快验证“闲置算力 + 双签租约 + 结果验证 + 内部积分”，刻意选择了
**单点权威**：

| 现状 | 影响 |
| --- | --- |
| Coordinator 是唯一任务权威/租约仲裁者 | 单点故障、单点审查；Coordinator 可拒绝服务或篡改状态 |
| 接入依赖静态 `peers` 白名单或一次性邀请码 | 不是无许可开放；每个新参与者仍需中心化准入 |
| Coordinator 使用本地 SQLite 单写者 | 无法多节点共享任务状态，无法水平扩展 |
| CREDIT 只存在本地账本 | 跨 operator 无法结算；余额与任务历史不可公开验证 |
| 任务发现/匹配在单 Coordinator 内存/本地 DB | 没有全局任务市场；匹配策略由单方决定 |
| 结果验证由 Coordinator 独立重算 | 验证者角色单一；争议无链上仲裁 |
| 无质押/惩罚/争议机制 | 恶意节点成本低，主要靠白名单与运维审查 |

这些限制在“小团队试用”阶段是可接受的；但用户明确选择 **开放公链，任何人注册可直接加入**，
目标与现有模型存在结构性冲突，需要分阶段演进，而不是给 Coordinator 加一个“公链接口”。

### 1.1 必须保留的安全不变量

公链化不得以“去中心化”为由削弱已经验证的执行安全：

1. 任务类型仍为白名单（当前 `numeric_batch_v1`），**不允许任意代码/eval/shell**；
2. 执行必须持有有效的双签租约（requester 签 terms，worker 签 acceptance，authority 签 commit）；
3. 没有有效 `LEASE_COMMIT` 不得执行；取消/过期/撤销的租约不得执行；
4. 结果必须独立重算验证，VALID 才产生结算；
5. CREDIT/结算必须可审计、不可双花、幂等；
6. 传输层公网必须 TLS；私钥永不上链、不进日志。

## 2. 目标与非目标

### 2.1 目标

- **开放加入**：任何持有密钥对的参与者可注册节点，无需人工邀请/白名单；
- **去中心化任务匹配**：任务发布、候选发现、匹配不再依赖单一 Coordinator；
- **可验证结算**：任务完成与积分/支付结算可被第三方验证，跨 operator 可组合；
- **渐进迁移**：现有任务执行、双签租约、白名单与验证语义保持兼容；
- **抗滥用**：开放网络下仍能抵抗 Sybil、垃圾任务、虚假结果、DoS 与合谋。

### 2.2 非目标（本 ADR 明确不做）

- 不立即发行代币、不做 ICO/空投、不承诺经济收益；
- 不从零自研 L1、共识客户端或 P2P 框架（复用 libp2p + 现有执行层）；
- 不实现任意代码执行、通用容器市场或隐私计算；
- 不宣称生产可用、不宣称已完成真实跨公网多设备验证（D6 仍未执行）；
- 不在本阶段修改 `ledger.py`/`state_machine.py` 的核心语义。

## 3. 关键决策点

### 3.1 a) 共识机制选型（暂不锁定，列出选项与权衡）

> 本 ADR **不选共识算法**，只规定选型标准与阶段性默认路径。任何自研共识都视为高风险。

| 选项 | 优点 | 缺点 | 适用阶段 |
| --- | --- | --- | --- |
| 现有 EVM L1/L2（Ethereum、OP/Arbitrum 等） | 成熟安全预算、EVM 工具、浏览器/钱包、审计生态 | Gas 成本、吞吐/确认延迟、依赖外部链 | Phase 1–3 的注册/结算锚定 |
| Cosmos SDK 应用链（Tendermint BFT） | 独立治理、IBC、可定制 | 需自建验证者集、运维/安全预算高 | Phase 2–3（若必须独立链） |
| 许可型 BFT/PoA（4–7 验证者） | 简单、低费用、可快速上线 | 验证者联盟、抗审查弱 | Phase 2 过渡/测试网 |
| PoS 公链自建 | 开放验证者 | 经济模型/罚没/攻击面复杂，审计成本高 | 不建议近期 |
| DAG/其他 | 高并发潜力 | 生态/工具/安全经验少 | 仅研究 |

**推荐（待批准）**：

1. **Phase 1 不引入共识层**：用一条现有公链（优先 EVM L2）的合约做“开放注册表/任务承诺锚点”，
   任务执行仍在现有 Coordinator/Worker 内完成；
2. **Phase 2** 若需要多 Coordinator，采用 **4–7 个验证者的 BFT/PoA 测试网**，先证明状态复制与争议流程；
3. **Phase 3** 结算迁移到现有公链/L2；除非有明确安全预算与审计，否则不自建 L1。

选型门槛：最终性时间、费用、验证者去中心化程度、合约可升级/治理、审计与生态工具、
以及“失败时能否回退到现有 Coordinator 模式”。

### 3.2 b) 身份与开放注册

- **身份根**：沿用 Ed25519 `node_id`（公钥即身份），链上只存 `node_id` 的哈希/承诺与
  TLS 证书指纹，不存私钥；worker/client 身份与链上地址解耦，可一个地址管理多个节点。
- **注册内容**：node_id、角色（worker/client）、端点（地址/端口/DNS）、TLS 证书指纹、
  能力清单哈希、注册时间、质押/保证金（可选）、版本。
- **开放方式（选项）**：
  1. 纯无许可注册：最低成本，但 Sybil/垃圾注册风险最高；
  2. **质押/保证金注册**（推荐 Phase 1 试点）：注册需锁定最小押金，违规可罚没；
  3. 工作量/服务证明注册：用历史完成任务/在线时长换取注册额度；
  4. 联盟准入（过渡）：验证者/运营方审批，保留邀请码作为降级路径。
- **推荐**：Phase 1 “读取无许可、写入需最小押金 + 速率限制”；Phase 2 引入服务历史/信誉；
  不强制全局 KYC，但保留运营方合规开关。

### 3.3 c) 积分/激励是否上链，与现有 CREDIT 的关系

- 当前 CREDIT 是本地账本事件，不可跨节点转移；直接改成链上代币会破坏现有语义与测试。
- **选项**：
  1. **纯链下 + 周期锚定**：CREDIT 保留本地账本，定期把 Merkle 根/总量锚定到链上；
  2. **非转让积分 + 链上承诺**：任务奖励用不可转让积分记录，链上只做承诺/争议；
  3. **可转让代币**：开放市场/流动性，但需经济、法律、安全审计；
  4. **双代币/质押**：治理代币 + 工作积分，复杂度最高。
- **推荐**：Phase 1–2 采用 **非转让积分 + 链上任务/结算承诺**；Phase 3 再决定是否发行可转让代币。
  迁移采用 **快照 + 1:1 自愿 claim**，保留旧账本只读；不做隐式兑换、不增发、不改变历史事件。
- 现有 `credit_holds` 的 HELD/SPENT/REFUNDED 语义在链上 escrow 中必须保持等价。

### 3.4 d) 任务权威与双签租约的演进

- 双签租约是执行安全的核心，**不废除**；变化的是“谁有权签 commit、状态存在哪里”。
- **推荐混合架构**：
  - 任务元数据、预算/escrow、任务承诺（task hash、requirement hash）上链；
  - 匹配/候选排序在链下（可验证、可复现），结果以签名消息提交；
  - requester 签 terms，worker 签 acceptance，**validator/协调者集合**签 commit；
  - worker 执行前验证 commit 的链上/链下有效性；没有 commit 不执行；
  - 结果验证由多个独立验证者重算，VALID 后触发 escrow 结算；
  - 争议进入链上挑战期/仲裁合约，超时按规则退款或罚没。
- Coordinator 角色演进为 **relayer/validator/sequencer** 之一，不再是唯一权威；
  Phase 1 可保留单 Coordinator 执行，仅把注册/承诺上链。

### 3.5 e) 安全与抗滥用

| 威胁 | 现有缓解 | 开放公链后需要新增 |
| --- | --- | --- |
| Sybil/女巫节点 | 静态 peers/邀请码 | 押金、服务历史、速率限制、验证者准入 |
| 垃圾任务/DoS | 任务池上限、限流、配额 | 任务发布押金、反垃圾费、优先费/配额 |
| 虚假结果 | 独立重算、签名校验 | 多验证者抽样、挑战期、罚没 |
| 合谋/刷量 | 单 Coordinator 审查 | 随机验证者、质押惩罚、信誉衰减 |
| 女巫领取任务 | 白名单 | 能力证明、历史绩效、随机分配 |
| 女巫攻击注册表 | 邀请码 | 注册押金、链上反 spam、地址年龄/信誉 |
| 验证者审查 | 单点 | 多验证者、退出/替换、可验证延迟 |
| 链上隐私 | 本地数据 | 任务内容哈希/承诺上链，原文链下；最小披露 |
| 密钥/证书 | TLS、密钥本地 | 证书指纹注册、轮换、吊销；HSM 可选 |
| 智能合约漏洞 | 无合约 | 审计、形式化/模糊测试、暂停开关、限额 |

开放网络必须新增 **威胁模型 v2**，并在每个 Phase 前完成滥用场景演练；禁止把“匿名/无许可”
当作“无滥用”。

## 4. 分阶段路径

### Phase 0：设计与验证（当前）

- 交付：本 ADR、威胁模型 v2 草案、链选型评分表、经济模型假设、迁移草案；
- 不写生产代码，不部署主网，不发行资产；
- 退出标准：评审通过选型（链/共识/身份/结算），明确 Phase 1 范围与回退方案。

### Phase 1：最小开放注册（建议 4–8 周）

- 目标：任何人可注册 node_id 并获得可验证的 open registry 记录，**任务执行仍由现有
  Coordinator 完成**；邀请码保留为降级/私有模式。
- 交付：
  - 注册表合约（或测试网合约）+ 链下索引器；
  - 注册 CLI（无邀请码；押金/速率限制）；
  - TLS 证书指纹注册与轮换；
  - 现有 Coordinator 从注册表读取候选（保留静态 peers 回退）；
  - 反垃圾/押金/黑名单最小机制。
- 不包含：代币、链上结算、多 Coordinator、去中心化匹配。
- 退出标准：测试网开放注册可持续运行，垃圾注册可控，现有任务闭环不回归。

### Phase 2：多节点与去中心化匹配（建议 8–16 周）

- 目标：多个 Coordinator/Validator 复制任务状态，匹配与 commit 不再依赖单点。
- 交付：
  - BFT/PoA 验证者集（4–7）或现有链上的多签/仲裁合约；
  - 任务状态复制/共识（先测试网）；
  - 可验证匹配（候选排序可复现）；
  - 多验证者结果抽样/挑战；
  - 故障转移、惩罚/退出。
- 不包含：可转让代币、完整经济治理。
- 退出标准：单节点故障不丢任务/不双花；争议可裁决；性能/延迟达标。

### Phase 3：链上结算与激励（建议 16 周+，需审计）

- 目标：CREDIT/奖励与任务 escrow 上链，跨 operator 可结算。
- 交付：
  - escrow/结算合约、退款/罚没、争议仲裁；
  - CREDIT 快照 + 自愿 claim；不可转让积分或代币（需单独 ADR）；
  - 审计（合约+经济）、监控、暂停/升级治理；
  - 迁移演练与回滚。
- 退出标准：审计通过、双花/重放/退款测试通过、法律/合规评估完成。

## 6. 对现有系统的影响评估

### 6.1 代码/模块

| 模块 | 影响 | 风险 |
| --- | --- | --- |
| `node.py` | 拆出注册/发现/验证者通信；Coordinator 角色多实例化 | 高（线程/状态机复杂） |
| `db.py` | 任务状态需可复制/可承诺；SQLite 仍可作为本地缓存 | 高（一致性/迁移） |
| `ledger.py` | 保持旧语义；新增结算适配器/锚定器 | 中（不得改历史） |
| `protocol.py` | 新增注册/承诺/验证者消息，保持 v2 兼容 | 中（版本协商） |
| `cli.py` | `invite/join` 保留；新增 register/stake/claim | 低-中 |
| 部署 | 合约、索引器、验证者、监控、密钥管理 | 高（运维/安全） |

### 6.2 工作量与团队

- Phase 0：1–2 人 × 2–4 周（设计/评审）；
- Phase 1：2–3 人 × 4–8 周（合约+索引器+注册 CLI+集成）；
- Phase 2：3–5 人 × 8–16 周（共识/复制/验证者）；
- Phase 3：3–5 人 × 16 周+（结算/审计/合规）；
- 需要新增角色：合约/安全审计、经济模型、运维/SRE、法务合规。

### 6.3 兼容与回退

- 保留现有邀请码/静态 peers/单 Coordinator 作为 **fallback mode**；
- 链上注册/结算可关闭，关闭后系统回到当前模式；
- 所有迁移只读旧数据，不重写历史；提供快照与回滚演练。
